# EXVS MSC Architecture Analysis

## See Also

- `docs/exvs-msc-syscall-4f-notes.md`
- `docs/exvs-msc-syscall-47-notes.md`

## 概述

这份文档用于说明 EXVS 系列中的 `msc` / `mscsb` 脚本架构、`E:\XB\解包\com\file\0xF1EF3B32\2.bin` 与其转译结果 `2.c` 所体现的运行方式，以及为什么游戏会把一部分“代码逻辑”落成 MSC 这种二进制脚本格式，而不是直接以原始高级语言文本或原生机器码的形式分发。

一个核心结论需要先说明：

- `2.c` 不是游戏原始源码。
- 它是反编译器为了便于人类阅读，选择用 C 风格语法表达 MSC 字节码语义的结果。
- 因此，更准确的说法不是“游戏把 C 直接编成 MSC”，而是“游戏把某种脚本逻辑编译成 MSC 字节码，反编译工具再把它近似还原成 C 风格代码”。

## 直接证据

### 1. MSC 不是原生可执行代码，而是脚本容器

从 `tools/mscdec_msc.py` 可以直接看出，MSC 文件是一个带有固定头、脚本表、指令流和字符串区的容器格式，而不是 CPU 原生指令文件。

关键证据：

- `MSC_MAGIC` 定义了文件签名。
- `MscFile.readFromFile()` 会读取：
  - 脚本区结束位置
  - 入口点 `entryPoint`
  - 脚本数量 `entryCount`
  - 字符串大小 `stringSize`
  - 字符串数量 `stringCount`
  - 脚本偏移表 `scriptOffsets`
- `MscScript.read()` 会把单个脚本段解析为 `Command` 列表。

这说明 MSC 的本质是：

- 一个脚本虚拟机可加载的资源文件。
- 文件内部包含多个脚本函数。
- 每个函数由一串虚拟机指令组成。

### 2. MSC 有独立的虚拟机指令集

`tools/mscdec_msc.py` 中定义了明确的 opcode 集合：

- 流程控制：`begin`, `end`, `jump`, `if`, `ifNot`, `else`, `return_*`
- 数据操作：`pushInt`, `pushShort`, `pushVar`, `setVar`
- 整数/浮点运算：`addi`, `subi`, `multi`, `divi`, `addf`, `subf`, `multf`, `divf`
- 比较与逻辑：`equals`, `notEquals`, `lessThan`, `greaterOrEqual`, `not`
- 引擎桥接：`sys`
- 函数相关：`try`, `callFunc`, `callFunc2`, `callFunc3`
- 类型转换：`intToFloat`, `floatToInt`

这些定义说明 MSC 是一个典型的 VM bytecode，而不是“被压缩过的 C”。

### 3. `2.c` 明显保留了 VM 脚本痕迹

从 `2.c` 可以直接看到大量高度脚本化的结构：

- `void main()` 作为脚本入口。
- 大量 `globalN` / `func_N` 命名，说明符号名已经丢失，只剩脚本编号与变量槽位。
- 大量 `sys_0(...)`、`sys_1(...)`、`sys_47(...)` 之类调用，说明脚本主要通过 syscall 与引擎交互。
- 存在 `callFunc3(func_4)`、`(*global1)()`、`global678 = func_901;` 这类函数指针和回调注册模式。

这更像“引擎提供 API，脚本通过 VM 调用引擎”，而不是“整个游戏逻辑都写在原生代码里”。

### 4. 样本 `2.bin` 具备脚本文件特征

针对 `E:\XB\解包\com\file\0xF1EF3B32\2.bin` 的头部做了快速检查，在当前工具约定的小端解析下可以看到：

- 文件大小约 `278256` 字节。
- 文件前部存在 MSC 家族识别头。
- 头部字段中可见脚本数量级信息，当前解析得到脚本数约为 `1057`。

虽然这个样本头部与 `pymsc` 中写死的标准头并不完全一致，但它仍然表现出同族 MSC 容器的结构特征，说明 EXVS 使用的是 MSC 的一个实际游戏变体，而不是完全不同的系统。

## 三个 Python 文件分别在做什么

## `tools/mscdec_msc.py`

这是 **MSC 格式层 / 指令集层**。

它负责：

- 定义 MSC 文件签名与核心结构。
- 定义 opcode 名称、参数格式、栈行为。
- 提供 `Command`、`MscScript`、`MscFile` 等基础对象。
- 把二进制数据拆成脚本和指令。

如果把整个系统分层，这一层相当于：

- 文件格式定义
- 虚拟机 ISA 定义
- 基础反汇编支撑

它回答的是“MSC 文件长什么样、每条指令长什么样”。

## `tools/mscdec.py`

这是 **反编译层 / 语义恢复层**。

它负责把底层 `Command` 序列恢复成更高层的语义结构：

- `getGlobalVars()` / `getLocalVarTypes()`：根据指令使用方式推断变量类型。
- `pullOutLoops()`：把跳转模式识别成 `while` / `do while`。
- `pullOutGroups()`：把函数调用、`if/else`、类型转换等从线性字节码里提取出来。
- `decompileCmd()`：把 opcode 映射成 AST 节点。
- `decompile()`：生成函数定义。
- `getFuncTypes()`：猜测函数返回类型。
- `printC()`：最终输出 C 风格代码。

也就是说，这个文件不是“读取 MSC”，而是在做更难的事情：

- 从栈机字节码恢复高级结构化控制流。
- 从匿名槽位恢复“看起来像源码”的形式。

它回答的是“如何把 MSC 读成人能理解的代码”。

值得注意的是，这份 `mscdec.py` 已经包含明显的 **EXVS2 专用后处理**：

- `handle_func_241_pointer_funcs()`
- `handle_sys_1_0x10001_0x10_var1_pointer_funcs()`
- `handle_var3_sys_0_0x700000_0_var1_0xa_pointer_funcs()`
- `convert_nested_if_else_to_switch()`

这说明通用 pymsc 反编译结果还不足以直接适配 EXVS2，作者额外对 EXVS2 常见的函数指针分发模式做了识别和替换，使输出更接近人类可读的逻辑。

## `tools/msclang.py`

这是 **编译层 / 回写层**。

它做的是反方向工作：

- 使用 `pycparser` 解析 C 风格源码。
- 将 AST 节点映射回 MSC opcode。
- 重新建立函数表、变量表、标签和脚本偏移。
- 把所有脚本重新序列化为 `mscsb`。

关键职责包括：

- `compileNode()`：把 AST 节点编译成 MSC 指令。
- `compileScript()`：把一个函数编译为脚本体。
- `resolveReferences()`：修正函数、标签、脚本地址引用。
- `writeToFile()`：写出二进制 MSC 文件。

同样，这个文件也带有 **EXVS2 变体兼容补丁**：

- `handle_EXVS2_2E_to_AE()`

这段逻辑会在特定字节模式匹配后，把某个 `0x2E` 改成 `0xAE`。这进一步说明：

- EXVS2 实际使用的 MSC 语义或编码细节与公开 pymsc 的默认假设并不完全相同。
- 当前工具链并不是“通用标准编译器”，而是“通用 MSC 工具 + EXVS2 定制修补”。

## 从 `2.c` 可以读出的架构特征

### 1. 脚本负责流程和状态，引擎负责能力

`2.c` 中大量是：

- `sys_0(...)` 获取状态
- `sys_1(...)` 设置状态或注册对象
- `sys_2(...)` 注册回调
- `callFunc3(...)` 调用脚本函数

这表明 MSC 并不直接实现底层系统，而是：

- 通过 syscall 访问引擎提供的能力
- 在脚本层拼装游戏流程、判断和状态机

换句话说：

- 引擎是宿主
- MSC 是逻辑编排层

### 2. 脚本大量依赖全局槽位和函数指针

例如：

- `global2 = func_43;`
- `(*global1)();`
- `global677 = func_904;`
- `global678 = func_905;`

这说明 MSC 很适合表达：

- 状态机
- 回调表
- 事件分发
- 动作表 / 行为表

这类逻辑如果写成原生代码当然也可以，但放进脚本 VM 里更容易统一调度。

### 3. `main()` 更像脚本入口，不像程序入口

`2.c` 里的 `main()` 做的不是系统初始化，而更像：

- 注册若干回调
- 初始化脚本全局状态
- 触发后续主逻辑

这与资源脚本入口的行为高度一致，说明这个文件对应的是某个游戏逻辑模块，而不是整个 EXVS 的原生程序本体。

## 为什么 EXVS 要把“代码逻辑”变成 MSC

下面这部分是基于直接证据做出的架构层推断。

### 1. 为了把“游戏逻辑层”与“引擎层”分离

这是最核心的原因。

引擎负责：

- 图形
- 输入
- 动画
- 音频
- 资源管理
- 对战框架

MSC 负责：

- 关卡/任务脚本
- 事件驱动逻辑
- 状态切换
- 回调注册
- 条件判断
- 参数选择

这样做的好处是：

- 引擎保持稳定。
- 逻辑层可以单独替换、更新、扩展。
- 新关卡、新模式、新行为可以更多靠资源与脚本驱动，而不是频繁改动底层程序。

### 2. 为了跨平台和跨版本复用

EXVS 系列经历了街机基板与后续多个版本迭代。把逻辑做成 VM bytecode 有明显收益：

- 只要宿主引擎继续支持 MSC VM，同一类脚本资源可以在多个版本中复用。
- 平台差异主要留在引擎实现层，脚本层不需要直接面对 CPU、ABI、编译器差异。
- 内容迁移、版本升级和资源打包更容易标准化。

这也是很多日系游戏引擎喜欢使用脚本 VM 或资源驱动逻辑的原因。

### 3. 为了内容生产效率

很多游戏并不会让策划或内容作者直接修改原生代码，而是给他们：

- 脚本语言
- 配置格式
- 事件表
- 行为描述文件

MSC 很可能就是这类内部工作流的落地产物：

- 高层作者写脚本或图形化逻辑
- 构建流程编译为 MSC
- 游戏运行时加载 MSC

这样可以减少直接修改原生程序的门槛，也便于批量打包资源。

### 4. 为了限制脚本能力并保证运行时可控

脚本 VM 的一个重要优势是“可控”。

MSC 指令集是有限的，脚本不能随意做宿主不允许的事，只能：

- 调用指定 syscall
- 访问约定变量
- 执行约定控制流

对商业游戏来说，这很有价值：

- 行为范围可控
- 内存访问更安全
- 调试边界更清晰
- 崩溃面更小

相比让逻辑直接跑原生代码，VM 更容易做沙箱化和一致性管理。

### 5. 为了数据驱动的回调和状态机组织

从 `2.c` 中可以看到大量函数指针、回调注册、事件派发和全局状态槽位。

这类系统很适合字节码表达，因为：

- 函数可以当作数据引用
- 回调表可以序列化进资源
- 状态切换和条件树天然适合 VM 执行

所以 MSC 更像“事件脚本 / 行为脚本格式”，而不是“通用高级语言的替代品”。

### 6. 为了发布与更新成本

把逻辑做成 MSC 资源文件还有工程层面的收益：

- 资源替换比重新编译完整程序更轻量
- 可以只更新某些脚本资源
- 打包、版本控制、差分更新更方便

对街机或大型游戏资源系统而言，这是非常实际的收益。

## 一个更准确的理解方式

与其说 EXVS 把“程序语言变成二进制 MSC”，不如说：

1. EXVS 引擎内部实现了一套 MSC 脚本虚拟机。
2. 某些高层游戏逻辑被编译为 MSC 字节码资源。
3. 游戏运行时加载这些脚本，并通过 syscall 把脚本逻辑接到引擎能力上。
4. 你现在看到的 `2.c` 只是为了分析方便，被反编译器重新表达出来的“近似源码”。

## 为什么反编译器会选择输出 C

这也是一个容易被忽略的问题。

原因通常不是“原始语言一定是 C”，而是：

- C 的表达能力足够接近底层栈机语义。
- `if/else`、`while`、`switch`、函数调用、指针、整数/浮点运算都能很好承载 VM 恢复结果。
- `pycparser` 生态成熟，既能反编译成 AST，也能再编译回去。

因此这套工具选择 C，更多是工程上的中间表示设计，而不是证明游戏原始脚本作者真的在写 ISO C 源码。

## 对当前工具链的判断

### 可以确定的部分

- 这三份 Python 代码构成了一套“MSC 解析 / 反编译 / 回编译”工具链。
- 基础设计继承自公开 pymsc 思路。
- 当前版本已经为了 EXVS2 做了明显定制。

### 需要保留谨慎的部分

- EXVS 原始内部脚本语言未必真的是 C。
- 你现在看到的 `2.c` 更像“反编译目标语言”。
- `2.bin` 的头部与通用 pymsc 定义并非完全一致，说明它可能是实际量产版 MSC 变体。
- `0x2E -> 0xAE` 这类补丁说明 EXVS2 某些 opcode 或编码位语义存在特化。

## 最终结论

EXVS 把一部分“代码逻辑”做成 MSC，本质上不是为了把源码“藏成二进制”这么简单，而是出于一整套成熟的游戏工程需求：

1. 将高层逻辑与底层引擎解耦。
2. 用有限指令集和 syscall 保持运行时可控。
3. 用资源化脚本支持回调、状态机、事件流程和内容扩展。
4. 提高跨版本复用、资源更新和内容生产效率。
5. 让游戏逻辑以 VM bytecode 的形式稳定运行在宿主引擎之上。

所以，MSC 更应该被理解为：

- EXVS 引擎中的脚本字节码格式
- 一种逻辑资源容器
- 一层连接“游戏内容逻辑”和“宿主引擎能力”的中间表示

而不是简单地把原本的 C 程序“压缩成 binary”。
