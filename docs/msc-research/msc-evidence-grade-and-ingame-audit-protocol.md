## 一句话

MSC `X.c` 是反编译产物，**语义几乎全部是推断出来的**。读源码只能确立「文件里写了什么」，
永远确立不了「引擎怎么解释它」和「玩家看到什么」。
把这三件事混成一件，就是不同 AI 对同一个 MSC 给出互相矛盾结论的**唯一根因**。

---

## 1. 为什么不同 AI 的 MSC 分析互相矛盾

不是模型能力差异，是**证据层被混用**。MSC 分析里存在三个不同的知识层：

| 层 | 问题形态 | 唯一合法证据 | 读 `X.c` 能不能回答 |
|----|----------|--------------|---------------------|
| **L1 语法** | 「`func_452` 里写了什么」「`0x928ca34f` 注册给谁」 | 读 `.c`、字节码回环 | **能** |
| **L2 引擎 ABI** | 「`sys_0(0x10000,0,0x11)` 是什么字段」「这个 hash 跑在哪一层」「它有没有 slot resolver」「`global3` 此刻是什么」 | 跨机体多份 vanilla 互证 / IDA native / 实机探针 | **不能** |
| **L3 玩家行为** | 「按下去会怎样」「能不能操控」「会不会自动解除」 | **只能实机** | **不能** |

`X.c` 里没有类型、没有字段名、没有 syscall 签名，`0.c` 与 `2.c` 之间还隔着一个不在任何文件里的引擎。
于是 L2/L3 的答案必须靠**外部证据**。当一个 AI 用 L1 的方法去回答 L2/L3 的问题时，
它会写出一条逻辑自洽、引用充分、看上去很扎实的推导链 —— 并且和另一个 AI 的推导链完全不同。
两条链都「有源码依据」，两条链都可能是错的。

**这就是「太肤浅」的真正含义：不是细节不够多，是证据等级不够。**
一份列了 40 个 `func_N` 调用关系的文档，如果它的结论是 L2/L3 的，那它的证据等级仍然是 L1。

### 1.1 木桶规则（本协议的核心）

> **一条结论的证据等级 = 它推导链上最弱一环的等级。**

推论，全部是硬规则：

1. **`源码钉死` 不能支撑 L2/L3 结论。** 无论读得多仔细。
2. 「我读了 `func_79` 的每个分支」不是证据，是**过程**。
3. 一份 `Status: 源码钉死` 的文档，**不允许**给出「必须这样改」的行为级政策，只能给出「源码里长这样」+「待实机」。
4. 跨机体互证（N 份 vanilla 机体在同一位置写法一致）可以把 L2 从推测升到 E2，但**升不到 E3**。

## 2. 证据等级 E0–E3

每份 MSC 文档、每条 `settled` 条目、每个 AI 改块，都必须带等级。

| 等级 | 含义 | 取得方式 | 可以做什么 |
|------|------|----------|------------|
| **E0** | 推测 / 未验证 | 只读了本机体 `.c`，或类比其它机体 | 只能写进「假设」段，**禁止**作为改动依据 |
| **E1** | 源码钉死（L1） | 本机体 `.c` 读通 + `mscdec` 回环确认字节码忠实 | 可以描述结构；**不能**断言运行期行为 |
| **E2** | 跨源互证（L2） | ≥2 份 vanilla 机体在同一角色上写法一致，或 IDA native 确认 | 可以断言引擎 ABI；行为仍待实机 |
| **E3** | **实机确认（L3）** | 打包进游戏、按预注册的判别式观察到结果 | 唯一可以断言玩家行为、唯一可以标 `实机确认成功` |
| **E3-** | **实机证伪** | 实机跑过并失败 | **价值最高**，必须进负面登记表 |

### 2.1 文档头格式（`tools/check_msc_doc_evidence.py` 会检查）

```markdown
**Status:** E3 实机确认成功（2026-08-25）；无杆惯性 E3（2026-08-27）
```

或分条目标注：

```markdown
| 结论 | 等级 | 依据 |
|------|------|------|
| 鸟形态 form id = `0x2` | E2 | TV 用 `0x1`，Rebellion `func_41` 发布 `0x2`，两边 `func_143` 对称 |
| 松杆会滑行后落地 | E3 | 2026-08-27 实机 |
| `0x928ca34f` 无 slot resolver | E3- | 实机：`func_65()` 后不接 `0x77b100ff`，原地卡 |
```

**混合等级的文档必须按段标注。** 整篇一个 `Status` 只在全篇同级时才允许。

## 3. 实机审计协议

游戏是唯一的 L3 oracle，但**每次实机都很贵**（改 `.c` → repack → 进游戏 → 对战场景 → 复现输入）。
所以协议的目标不是「多测」，是**每次实机榨出最多信息**。

### 3.1 预注册证伪（打包前必须写下来）

在**动手改之前**，把这三行写进文档或提交说明：

```text
H  假设:      30 帧后交棒给 0x77b100ff，玩家获得原生飞行操控
P  预测:      推杆能改变航向；松杆约 1 秒内自动解除回普通形态
F  证伪判据:  若「不能转向」或「不会自动解除」中任意一条成立，H 被证伪
```

没有预注册的 `F`，实机回来只会得到「没用」，然后下一轮继续猜。
**「没用」不是实机数据，`F` 才是。**

### 3.2 单变量原则

一次 repack 只改**一个**会影响判据的变量。
本次会话反例：同一个包里同时改了「冲刺速度公式」和「30 帧后的交棒机制」，
实机回报「不移动」时，无法区分是速度变 0 还是交棒卡死 —— 一次昂贵的实机只换回一个二义结果。

### 3.3 判别式：怎么在实机里分辨「看起来一样」的两种状态

MSC 没有 `printf`，但**状态差异必须被设计成可观察的**。常用判别式：

| 现象 | 候选状态 A | 候选状态 B | 判别输入 |
|------|-----------|-----------|----------|
| 变成飞行外观但不前进 | 卡在脚本自绘 loop | 已进原生 `0x77b100ff` | **推杆能否转向**：能=B，不能=A |
| 人在飞但动作是站姿 | 动作换了、`global143` 没清 | form 清了、移动通道还在写 | 按格斗：出鸟近战=form 还在；出地面格=form 已清 |
| 冲刺完停住 | mag 被写成 0 | `func_296(0x3e8,0)` 关了电机 | 是否仍缓慢下坠：缓降=mag 0；直坠=电机关 |
| 招式没出来 | 取消窗没开 | hash 提交了但没落地 | 原版招是否照常播完：播完=窗没开 |

### 3.4 实机探针：给 MSC 装 `printf`

这是本仓库一直缺的手段。MSC 有**三条对玩家可见的旁路输出**，可以当调试通道：

| 通道 | 写法 | 观察点 | 成本 |
|------|------|--------|------|
| **SE** | `sys_58(0, <se_hash>)` | 听声音 | 最低，推荐 |
| **Effect** | `sys_4A(0, <fx_hash>, global20, 0x1, <group>, 0)` | 看特效 | 低，但占 group 槽 |
| **Motion** | `func_74(<slot>, 0)` | 看动作 | 会改观感，仅用于确认分支 |

探针用法（**必须包在 AI 块里，验证完立刻删**）：

```c
// AI decision (YYYY-MM-DD): temporary in-game probe, remove after verification.
// Fires only on the phase-2 branch so the player can hear whether the handoff
// branch was reached at all. global240 gates it to one shot per action.
// Origin: AI-assisted MSC edit; in-game audit protocol §3.4 probe.
if (probe_fired == 0)
{
    probe_fired = 0x1;
    sys_58(0, 0x46a7a8a6);
}
// End, origin is AI-assisted MSC edit; temporary in-game probe.
```

一次实机可以放**两个不同 SE** 的探针，就能把「A 分支进没进」「B 分支进没进」一次问清楚，
把二义的「没用」变成 4 种可区分结果。这比再读 500 行反编译便宜得多。

### 3.5 实机回报模板（给用户填的最小集）

```text
输入:        特格 → 格斗
看到:        变形动画播了，然后原地不动
推杆:        不能转向          <- 判别式 3.3
松杆:        不会自动解除
探针 SE-1:   响了              <- 进了 release 分支
探针 SE-2:   没响              <- func_452 从未执行 => 交棒未落地
```

有这五行，结论是**确定**的，不需要再猜。

## 4. 审计一份既有文档的步骤

对 `docs/msc-research/` 里任意一份旧文档：

1. **分句标层。** 每条结论标 L1/L2/L3。
2. **查链。** L2/L3 结论向上找证据；找不到实机记录的一律降级 **E0**，不要因为「写得很详细」就默认它是对的。
3. **查冲突。** 与 [负面登记表](./msc-falsified-negatives-registry.md) 对撞；命中即标 `E3- 已证伪`。
4. **查代码。** 文档描述的函数/符号是否还存在于当前 `.c`（本次审计发现文档与树可以严重不同步）。
5. **标注，不删除。** 旧结论降级保留并注明降级理由；删掉会让下一个 AI 重新踩。
6. **回填 catalog。** 新确立的 E3 / E3- 必须写进 `tools/msc_research_catalog.py` 的 `settled` / `do_not`，否则等于没记录。

## 5. 反例：2026-08-27 会话完整失败链（必读）

这是本协议每一条规则的来源，按发生顺序：

| # | 动作 | 违反了什么 | 结果 |
|---|------|-----------|------|
| 1 | `ls docs/msc-research/` 然后按文件名挑了 3 份「flight」文档读 | AGENTS.md 明确禁止列目录，要求先 `--match` | 漏掉了本功能的 owner 文档 `wing-zero-rebellion-special-n-bird-dash.md` |
| 2 | 用 L1 方法推导「`0x928ca34f` 结束后 0.c 会接 `0x77b100ff`」 | §1.1 木桶规则 | 该结论在 owner 文档里已被 **E3- 明文证伪**：「`0x928ca34f` 不是 `func_13` 的 slot hash，没有 `func_35/36` resolver」 |
| 3 | 提交 `func_81(0x9475130e, …)` + 重启 `0x3d` | 同上 | 两条都在 owner 文档「作废路径」表里，均已实机失败 |
| 4 | 同一个包里同时改速度公式和交棒机制 | §3.2 单变量 | 实机回报「不移动」无法定位 |
| 5 | 没有预注册证伪判据 | §3.1 | 只拿回「没用」，信息量≈0 |
| 6 | 反编译回环确认字节码忠实后，据此判断「逻辑没问题」 | §1.1：回环是 **E1**，证明不了行为 | 把 E1 当成了行为证据 |

**代价：两次 repack、一次完整实机、用户手工回退整棵树。**
**如果第 1 步跑了一次 `--match`，全部可以避免** —— 实测该 cluster 对 5 种自然查询都排第一（见审计报告 F3）。

## 6. 硬规则清单

1. 动 MSC 之前**必须**先 `python tools/msc_research_catalog.py --match "<关键词>"`，禁止列 `docs/msc-research/`。
2. 提出任何改法之前**必须**对撞 [负面登记表](./msc-falsified-negatives-registry.md)。
3. L2/L3 结论**禁止**以「读了源码」结案，必须标 E0 或走实机。
4. 每次 repack 前**必须**写下 H / P / F 三行。
5. 一次 repack 只动一个判据变量。
6. 状态二义时**先加探针**，不要先加推导。
7. 实机失败的结论**必须**回填负面登记表 + catalog `do_not`，这是本仓库最贵的资产。
8. 文档与 `.c` 不同步时，**以 `.c` 为准并立即修文档**，不要在过期文档上继续推理。
