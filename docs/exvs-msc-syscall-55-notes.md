# EXVS MSC Syscall 55 Investigation Notes

## 概述

这份文档记录当前针对 `sys_55`（`0x55`）的阶段性分析结果，重点是明确它在脚本里“怎么用”和“在系统里扮演什么角色”。

建议结合以下文档一起阅读：

- `docs/exvs-msc-analysis.md`
- `docs/exvs-msc-syscall-54-notes.md`
- `docs/exvs-msc-syscall-53-notes.md`

---

## 当前最强结论

基于 `CDepictionScript` 挂载函数 `sub_140664F70`：

- `a1[89] = sub_1406837C0`（data xref: `0x1406650A4`）
- 映射模型：`syscall_id = slot_index - 4`
- 因此：`slot 89 -> syscall 85 -> sys_55 -> sub_1406837C0`

`sys_55` 不是镜头角度/插值接口，而是一个 **ID 分类状态管理接口**：

- `subcmd 0`: 批量重置
- `subcmd 1`: 设置指定 ID 的状态
- `subcmd 2`: 查询指定 ID 当前命中数量

---

## Native Handler 形态

`sub_1406837C0` 特征：

- 结构非常小（size `0xBA`）
- 只有 3 个有效分支（`*a4` 为 `0/1/2`）
- 主数据对象在：
  - `*(_QWORD *)(*(_QWORD *)(a2 + 40) + 10816)`

这是一种典型的“分类表/槽位表”访问模式，不是相机参数块写入模式。

---

## 子命令语义（当前版本）

### `sys_55(0)` -> `subcmd 0`（高置信）

行为：

- 调用 `sub_1405FB1E0(table)`
- 遍历 32 个槽位（每槽 96 bytes）
- 把满足条件的槽位状态置为 `3`

脚本侧典型调用：

- `sys_55(0);`（如 `func_845` 初始化流程）

结论：

- 全局清理/重置这套 ID 状态表。

---

### `sys_55(1, id)` / `sys_55(1, id, flag)` -> `subcmd 1`（高置信）

行为：

- `id` 先经 `sub_140682280` 映射到合法范围（`0..22`，非法变 `-1`）
- 调用 `sub_1405FB220(table, &id, mode)`
- `mode` 默认是 `2`
- 若第三参数存在且非 0，则 `mode` 变为 `1`

脚本侧高频形态：

- `sys_55(0x1, 0x6);`
- `sys_55(0x1, 0x2, 0x1);`

结论：

- 给某个“分类 ID”写入状态（至少有两种写法：mode 1 / mode 2）。

---

### `sys_55(2, id)` -> `subcmd 2`（高置信）

行为：

- 同样先将 `id` 映射到 `0..22`
- 调 `sub_1405FB080(table, &id)` 返回命中数

脚本侧用法：

- `if (sys_55(0x2, 0x10) > 0) ...`
- `if (sys_55(0x2, 0x11) > 0) ...`
- `if (sys_55(0x2, 0x12) > 0) ...`

结论：

- 查询某个 ID 是否“当前有效/命中”（返回数量，脚本常按布尔判断）。

---

## ID 参数范围与意义

`sub_140682280` 明确只接受：

- `0 ~ 22`

超出范围：

- 返回 `-1`

从脚本实用习惯看：

- 常写入的 ID：`1,2,3,6,7,8,0xA,0x13,0x14`
- 常查询的 ID：`0x10,0x11,0x12,0x2`

这说明该系统更像“固定枚举事件/类别开关”，而不是自由 hash 参数。

---

## 脚本层面的真实作用（当前推断）

`sys_55` 在实战流程中通常承担：

- 初始化阶段批量置位多个 ID（`subcmd 1`）
- 运行阶段轮询关键 ID 是否命中（`subcmd 2`）
- 场景切换或重开时一键清空（`subcmd 0`）

它更像一个 **事件类别门控 / 状态触发表**，而不是直接执行镜头动作的接口。

---

## 与 `sys_53/54` 的关系

- `sys_53`：镜头 preset 与通道插值
- `sys_54`：镜头姿态/角度限制
- `sys_55`：分类 ID 状态标记与查询（用于驱动脚本分支）

三者在同一 depiction family，但职责不同。

---

## 深入：`sys_55` 背后的判定表机制

从 `sub_140694730` 到 `sub_1405F87E0` 的调用链可以看到：

- `0x70006` 命令会调用 `sub_1405F87E0(..., +10816, +10824)` 更新判定表
- `+10816` 是一张 32 槽位表（每槽约 96 bytes）
- `sys_55` 的 set/query/reset 都直接操作这张表

`sub_1405F8290` 会对单个目标做空间判定（距离 + 角度）：

- 计算目标相对方向与仰角（可见 `atan2f`）
- 使用两条阈值函数 `sub_1405F86A0 / sub_1405F8520`
- 输出一个离散判定等级（常见值 `1/2/3`）和附加标记

因此 `sys_55` 更接近“目标/事件判定结果总线”，而不是简单手工 flag。

## 深入：ID 的已知影响（可验证）

### ID `0x13`（=19）会影响判定阈值（高置信）

`sub_1405F8520` / `sub_1405F86A0` 都会查询：

- `sub_1405FB080(table, id=19)`

命中后阈值乘 `0.9f`（判定更严格/更紧）。

而脚本里确实经常设置：

- `sys_55(0x1, 0x13)` 或 `sys_55(0x1, 0x13, 0x1)`

这说明 ID `19` 不是普通占位符，而是会改变核心判定曲线。

### ID `0x03` 会影响另一条判定支路（高置信）

`sub_1405F89C0` 查询：

- `sub_1405FB080(table, id=3)`

命中时把某系数从 `1.0` 改为 `1.2`（常量 `0x3F800000 -> 0x3F99999A`）。

脚本中也有高频：

- `sys_55(0x1, 0x3)`

说明 ID `3` 也是实质性的判定调节项。

### ID `0x10/0x11/0x12`（中置信）

脚本 `func_23` 中：

- `sys_55(0x2, 0x10) > 0` -> `global64 = 2`
- `sys_55(0x2, 0x12) > 0` -> 首次触发 `sys_4F(0x13)`
- `sys_55(0x2, 0x11) > 0` -> 首次触发 `sys_1(0x60012, 0x64)`

这三项像是“运行中事件触发类 ID”，目前仍缺名字，但可确认它们是动态命中信号，不是静态配置。

## 游戏内实际效果（当前最接近体感的解释）

结合脚本调用链（`func_23 -> func_38`）可以把 `sys_55` 的游戏表现归纳为：

1. **持续判定输入**  
   native 每轮更新判定表（距离+角度），`sys_55(2, id)` 只是“读命中结果”。

2. **命中事件转成短时系统脉冲**  
   例如 ID `0x10` 命中会把 `global64` 置 `2`，随后在 `func_38` 里触发：
   - `sys_1(0x30003, 0x1)`（短脉冲）
   - 下一拍自动回 `sys_1(0x30003, 0)`

3. **命中事件转成演出/反馈触发**  
   - ID `0x12` 命中时首次触发 `sys_4F(0x13)`
   - ID `0x11` 命中时首次触发 `sys_1(0x60012, 0x64)`

4. **脚本阶段门控**  
   某些流程（例如 `func_746`）会把 `sys_55(2, 0x2)` 当作条件：
   - 未命中则推进阶段并调用 `sys_55(1, 0x2)` 改写状态

换句话说，`sys_55` 在游戏里的作用是：

- **“感知判定 -> 事件命中 -> 推动反馈与状态机分支”**  
- 它通常不直接产生镜头动作，而是驱动别的 syscall（`sys_1/sys_4F`）去做可见反馈。

- `+10816` 这张 32 槽表在其他系统中的写入来源（除了 `sys_55` 外还有哪些 producer）。
