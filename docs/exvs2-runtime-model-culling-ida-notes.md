# EXVS2 Runtime Model Culling IDA Notes

Date: 2026-06-22

Target binary:

- `E:\OBHK0.3_v27\vsac27_Release.exe`
- IDB: `E:\OBHK0.3_v27\vsac27_Release.exe.i64`
- Image base: `0x140000000`

## Problem

Large converted SSBH unit models can disappear in-game when the camera no
longer includes the model center. A ship can render correctly when its center
is visible, but if only the bow or stern remains on screen, the whole main
model disappears. The shadow can still render.

Current working assumption from testing:

- This is not caused by `.numatb`.
- This is not caused by `.numshb` file bounds.
- This is not caused by shell resource layout.
- Continue from runtime/IDA evidence only.
- Avoid dynamic-memory patching or live process memory changes for this phase.

## Current Conclusion

The strongest current hypothesis is:

> Main model rendering is gated by a runtime visibility key / slot table. The
> long model is represented by a key tied to a central runtime visibility slot.
> When the camera no longer includes that central slot, the key becomes invalid
> for the main render path, so the whole main model is skipped. Shadow rendering
> uses a different pass/queue path and can still draw the geometry.

This explains why file-side material and mesh-bound changes did not affect the
symptom.

## Main Render Evidence

### `sub_1405D00A0`

This function processes render command buckets and eventually submits visible
objects to the main render manager.

Important path:

```asm
1405D05C1  call qword ptr [rax+0D0h]   ; object method writes a visibility key
1405D05C7  test dword ptr [rsp+20h], 7000000h
1405D05CF  jne  1405D05F5              ; special key path
1405D05DA  call sub_1405E26E0          ; ordinary key validation
1405D05DF  test al, al
1405D05E1  jne  1405D05F5              ; valid key proceeds
1405D05EE  call qword ptr [rax]        ; invalid key: release/skip object
1405D0682  call sub_1405F79D0          ; submit to main render manager
```

The important point is that the object can be skipped before `sub_1405F79D0`
even if the model resource itself is valid.

### `sub_1405E26E0`

This validates ordinary runtime visibility keys.

Key format inferred from the function:

- bit 31 must be set.
- bits `0..11`: slot index, must be `< 0x18`.
- bits `12..23`: generation/version.
- bits `24..26`: special type bits. If these are set, the caller may use a
  separate special-key path instead.

Validation logic:

```c
if ((key & 0x80000000) == 0)
    return false;
if ((key & 0x07000000) != 0)
    return false;
slot = key & 0xFFF;
generation = (key >> 12) & 0xFFF;
return table_generation[slot] == generation && table_object[slot] != 0;
```

So this is not testing `.numshb` AABB/sphere data. It is testing the current
runtime visibility table.

### `sub_1405F7630`

This generates and writes the runtime visibility key into the object.

```asm
1405F76B2  mov dword ptr [rsi+520h], eax
```

`object + 0x520` is the same field previously seen as `object + 1312`.

Call chain:

```text
sub_1405F79D0
  -> sub_1405F7220
     -> sub_1405F7630
        -> writes object + 0x520
```

This confirms the key is generated by the runtime render manager, not by the
asset file.

### `sub_1405CFF30`

This validates special keys, not ordinary keys.

It accepts only keys with special type bits corresponding to type `1` or `2`.
Ordinary type `0` keys must go through `sub_1405E26E0`.

This matters because the disappearing ship appears to behave like an ordinary
visibility-key object, not a special always/alternate visibility object.

## Visibility Table Rebuild Evidence

`sub_1405C01E0` appears to rebuild or process the per-frame visibility state.
Important signs:

- It enumerates runtime keys from a tree/map.
- It calls `sub_1405E4FE0`, `sub_1405E5150`, and `sub_1405E4DE0`.
- It reads 24-slot visibility data with a stride of `7456`.
- It checks a per-slot byte at offset `+7448`.
- It uses per-slot data around offset `+2704`.
- It updates counters around `+55608` and `+55704`.

This is the next best static-analysis target, because it likely explains why a
slot becomes invalid when the camera leaves the central region.

### Frame Order

`sub_1405D5040` shows the relevant per-frame order:

```text
sub_1405CDF70(manager)
sub_1405CE0D0(manager, ...)
sub_1405CE1B0(manager, ...)
sub_1405CDA50(manager)
sub_1405CD980(manager)
sub_1405C01E0(visibility_context)
sub_1405E5920(...)
sub_1405D57D0(...)
sub_1405D00A0(render_context, command_context)
```

So the key/visibility state is rebuilt before final main render submission.
`sub_1405D00A0` consumes the result of that rebuild.

### `sub_1405C01E0` Key Graph Behavior

`sub_1405C01E0` does not enumerate mesh objects or material resources. It
enumerates runtime keys from the tree/map at:

```text
*(*(_QWORD *)(visibility_context + 16) + 8) + 208
```

The enumerator is `sub_140365C10`, which copies up to 64 runtime keys into a
temporary array and stores the count at `array[128]`.

The function then repeatedly checks:

- `sub_1405E4FE0(context, key)`
- `sub_1405E5150(context, key)`
- `sub_1405E4DE0(context, out_related_key, key_ptr)`

Important inferred behavior:

- `sub_1405E4FE0` checks whether the key maps to an object whose state pointer
  at `object + 0x2E68` (`+11880`) has state `2`.
- `sub_1405E5150` checks that the mapped object has a valid secondary key at
  `object + 0x520` (`+1312`).
- `sub_1405E4DE0` maps a valid key to the related key stored at `object + 0x480`
  (`+1152`).

When a key is not already state `2`, `sub_1405C01E0` may look up its slot data:

```text
slot_data = base + 7456 * slot_index + 16
if (*(slot_data + 7448) == 0)
    slot_data = 0
```

If `slot_data` exists, the function reads data around:

```text
slot_data + 2704
```

That block contains up to two related key references. These references are used
to add keys into internal lists and increment counters around:

```text
context + 55608
context + 55704
```

This reinforces that visibility propagation is based on a runtime key graph and
slot state, not the SSBH mesh bounds.

## Runtime Grid Evidence

`sub_1405CD980` runs before `sub_1405C01E0` and updates a 2D grid from runtime
objects.

It iterates objects from the manager list at `manager + 96 .. manager + 104`.
For objects with byte `+104` set, it clears that byte and calls the object's
vtable method at `+0x30`:

```text
object->vtable[6](object, &min, &max)
```

If that method returns true, only the X/Z rectangle is passed to:

```text
sub_1405C7B70(manager + 264, min.x, min.z, max.x - min.x, max.z - min.z)
```

`sub_1405C7B70` maps that rectangle into a 20-unit 2D grid and expands it by a
small fixed margin (`20` to `40` units in the observed formulas). It then marks
or evaluates cells through:

- `sub_1405C8460`
- `sub_1405C81F0`

`sub_1405C7F60` also uses global camera/view state from `qword_14241E880` and
then calls `sub_1405C7B70` over the whole grid range.

Current interpretation:

- The grid is based on runtime object/proxy bounds, not directly on `.numshb`
  mesh bounds.
- If the ship model is represented by a smaller shell/gameplay proxy, changing
  mesh file bounds would not change this grid input.
- This aligns with the observed center-dependent behavior.

### Proxy Driver Registration And AABB Source

`sub_1405CA380` is the currently identified registration/creation point for the
runtime proxy objects consumed by the `manager + 96 .. +104` list.

It creates two related stage object driver classes:

- `sub_1405F0010`: constructs
  `VDK::GAM::CStageObjectDriverStationary`, allocation size `0x6A0`.
- `sub_1405F0920`: constructs
  `VDK::GAM::CStageObjectDriverPhysicsProp`, allocation size `0x6E0`.

When `sub_1405CA380` is called with `a5 == 0`, it pushes the created driver
object into:

```text
manager + 96 .. manager + 104
```

That push goes through `sub_1405CF0E0`, an 8-byte vector push helper. It has
only one code xref, from `sub_1405CA380`, which makes this a focused and useful
registration point.

Important vtable slots for both driver classes:

```text
+0x10  relation/update entry output
+0x30  sub_1405EF840  returns cached AABB
+0x48  sub_1405EF580  refresh cached AABB and clear dirty flags
+0x70  Stationary: no-op/debug stub
+0x70  PhysicsProp: sub_1405F29F0
+0x78  final setup hook
+0xC0  driver type / key type helper
```

`sub_1405EF840`, the vtable `+0x30` method called by `sub_1405CD980`, does not
compute bounds. It only returns cached proxy bounds:

```c
*out_max = *(_OWORD *)(object + 1392);
*out_min = *(_OWORD *)(object + 1376);
return *(uint8_t *)(object + 1360);
```

The cached AABB is initialized to invalid/zero by the common base constructor
`sub_1405EE0E0`:

```c
*(uint8_t *)(object + 1360) = 0;
*(_OWORD *)(object + 1376) = 0;
*(_OWORD *)(object + 1392) = 0;
```

The cached AABB is populated by `sub_1405EF340` and `sub_1405EF410`. Both call:

```c
sub_1402FD840(model_instance, object + 1376, object + 1392);
*(uint8_t *)(object + 1360) = 1;
*(uint8_t *)(object + 104) = 1;
```

`object + 104` is the dirty/update byte later consumed by `sub_1405CD980`.
Therefore the grid update chain is:

```text
sub_1405EF340 / sub_1405EF410
  -> sub_1402FD840(model_instance, object+1376, object+1392)
  -> object+1360 = 1
  -> object+104 = 1
sub_1405CD980
  -> object->vtable+0x30 == sub_1405EF840
  -> sub_1405C7B70(manager+264, min.x, min.z, max.x-min.x, max.z-min.z)
```

`sub_1402FD840` computes the AABB by iterating the runtime model instance's
parts:

```c
count = model->vtable[4](model);         // vtable +0x20
for (i = 0; i < count; i++) {
    part = model->vtable[5](model, i);   // vtable +0x28
    if (*part == 0xFFFFFF)
        continue;
    sub_140AA3080(model[1] + 32, *part, &part_minmax);
    min = min(min, part_min);
    max = max(max, part_max);
}
```

`sub_140AA3080` is the leaf used to read each part's bounds. It indexes a
176-byte part record with `part_index & 0xFFFFFF` and reads bounds from that
record:

```c
record = base + 176 * (part_index & 0xFFFFFF);
max = *(__m128 *)(record + 96);
min = shuffle(*(uint64_t *)(record + 112), max);
```

This is a stronger form of the earlier grid hypothesis:

> The main-render grid uses cached AABB on the runtime stage object driver.
> That cached AABB is derived from a runtime model instance's active part list,
> not from a direct read of `.numshb` file bounds during culling.

This still fits the observed shadow behavior. A shadow pass can render from a
different path while the main render proxy/grid says the stage object driver is
outside or inactive for the current camera region.

### Runtime Proxy List Evidence

`sub_1405CDA50`, `sub_1405CDF70`, `sub_1405CE0D0`, and `sub_1405CD980` all work
with the manager object list at:

```text
manager + 96 .. manager + 104
```

This list does not look like a raw draw-mesh list. The objects expose several

- vtable `+0x18`: post-processing after relation expansion.
- vtable `+0x28`: update/notify method.
- vtable `+0x30`: writes AABB min/max used by `sub_1405CD980`.
- vtable `+0x80`: invoked for certain group states in `sub_1405CDE40`.

`sub_1405CDA50` rebuilds a vector at `manager + 232 .. +240` from these 12-byte

```text
entry[0] = type
entry[1] = index/group
entry[2] = extra value
```

Observed behavior:

- Type `0` entries go through `sub_1405CDE40`.
- Type `1` entries go through `sub_1405CDCC0`, which asks another proxy object

- `sub_1405CDE40` uses the entry index to access a 896-byte group record and

- `sub_1405CE0D0` consumes command `536870914` (`0x20000002`) and updates a

This makes the working model more specific:

> The main visibility decision is driven by runtime proxy objects and their

## Visibility Command Bridge

`sub_1405C01E0` emits command `0x20000018` (`536870936`). This command is later
consumed after visibility rebuild and before final render submission.

Frame path:

```text
sub_1405D5040
  -> sub_1405C01E0
  -> sub_1405E5920
     -> sub_1405E5870
        -> consume command 0x20000018
        -> sub_1405E5D90
  -> sub_1405D57D0
  -> sub_1405D00A0
```

`sub_1405E5870` scans the command queue for `0x20000018` and passes command
fields into `sub_1405E5D90`.

`sub_1405E5D90` records the result by key. It accepts a record if:

```text
key == -1
or (sub_1405E5150(context, key) && !sub_1405E4FE0(context, key))
```

Then it stores:

- category/index from the command,
- the key,
- another command pointer/value,
- four 16-byte blocks from the command payload,
- bitsets keyed by the runtime key.

`sub_1405D57D0` later consumes these key-grouped records and calls
`sub_1405E2770` repeatedly.

`sub_1405E2770` is another state-2 check:

```c
slot = sub_140365310(table, key);
object = table_slot_object[slot];
return object && **(_DWORD **)(object + 11880) == 2;
```

This extends the evidence chain:

```text
runtime proxy entries
  -> command 0x20000018
  -> key-grouped visibility records
  -> state-2 checks
  -> final main render submission gate
```

The chain still does not depend on `.numshb` mesh bounds or `.numatb`
parameters.

## Static Verification Candidate

The key static verification is to prove one of these:

1. The object's ordinary visibility key is tied to a central runtime slot, and
   that slot is removed from the current table when the camera no longer sees
   the center.

2. The per-frame visibility rebuild ignores the full model mesh bounds and uses
   shell/gameplay object bounds or a smaller proxy.

Either result would explain why the main mesh disappears while the shadow can
remain.


## Verified Findings (2026-06-22, Continued IDA Session)

This section records the results of the targeted static verification described
in the previous section. All offsets and pseudocode were re-derived directly
from `vsac27_Release.exe.i64` (image base `0x140000000`) in this session.

### Decisive Conclusion

The disappearance is caused by the **runtime keyed visibility-slot system**, not
by `.numshb` mesh bounds or `.numatb` materials. The main render path registers
each renderable object into a **fixed 24-entry slot table** and re-validates the
object's runtime key (`object + 0x520`) every frame. The set of objects that get
registered each frame is driven by the **per-frame proxy/grid visibility set**,
which is built from the runtime stage-object driver's cached AABB rasterised into
a 20-unit 2D X/Z grid.

This confirms verification candidate **#1** (the object's ordinary visibility key
is tied to a runtime slot that is not re-populated when the camera region
changes) and refines candidate **#2** (the gate is the proxy/grid registration
order, not a literally "smaller" proxy AABB).

### Submission Branch: `sub_1405F79D0`

`sub_1405F79D0(manager, object)` is the single entry point that registers an
object for main render. It branches on the object's **key type** from vtable
`+0xC0`:

```c
type = object->vtable[0xC0]();          // 0, 1, or 2
if (type == 0)
    return sub_1405E2490(manager + 8, object);    // type 0: bitmask slot pool
sub_1405F7220(manager + 640, object);             // type 1/2: round-robin slot pool
if (type == 1)
    return sub_140619A10(*(manager + 696), object);
```

Both pools are independent but both are **hard-capped at 24 slots** by every
consumer (`sub_1405E26E0`, `sub_1405E4FE0`, `sub_1405C01E0` all throw
`_Xout_of_range` for `slot >= 0x18`).

### Type-0 Slot Allocator: `sub_1405E2490`

This is the path ordinary models take. It is a 24-bit free-slot bitmask
allocator:

```c
// a1 = registration table, a2 = object
if (*(a1 + 600) == -1)        // a1+600 = 24-bit free-slot bitmask
    return;                   // ALL 24 SLOTS USED -> object silently dropped
free   = ~(*(a1+600)) & (*(a1+600) + 1);          // isolate lowest free bit
slot   = dword_141AAE730[(0x22FDD63CC95386D * free) >> 58];  // De Bruijn index
*(*(a2 + 11800) + 20) = slot;                      // store slot in render-state
if (slot >= 0x18) throw;                           // HARD CAP 24
*(a1 + 8 * slot + 8) = a2;                          // slot_array[slot].obj = object
sub_1405E21C0(a1 + 200, ..., a2 + 1152);           // insert related key into RB-tree
*(a1 + 600) |= (1 << slot);                         // mark slot used
```

Key consequences:

- If 24 objects are already registered this frame, the 25th and beyond receive
  **no slot, no key, and no tree entry**. Their main render submission later
  fails the key check and is skipped.
- The related key inserted into the red-black tree at `a1 + 200` is the same tree
  walked by `sub_140365310` (returns `node[10]` = slot). This closes the
  key -> slot lookup loop.

### Type-1/2 Slot Allocator: `sub_1405F7220`

Round-robin allocator over a growable 16-byte-entry vector:

```c
// find slot with obj == 0, advancing round-robin from last index, wrapping to 0
// if none free (wrapped fully) -> push a NEW entry (slot index = old capacity)
slot_array[slot].obj = object;
sub_1405F7630(pool, object, slot);    // generate key for this slot
```

The vector can grow past 24, but `sub_1405E26E0` / `sub_1405E4FE0` reject any
`slot >= 0x18`, so grown entries are never valid for main render.

### Key Generator: `sub_1405F7630`

```c
gen = ++(*(pool + 48));                 // generation counter
CompareExchange(pool + 48, 0, 4095);    // wraps at 4095
slot_array[slot].gen = gen;             // *(slots + 16*slot + 8) = gen
type = object->vtable[0xC0]() & 7;
key  = (slot & 0xFFF)
     | (((gen & 0xFFF) | ((type | 0xFFFFFF80) << 12)) << 12);
object[328] = key;                      // object + 0x520
```

So the runtime key encodes `slot | generation | type`. The slot validator
`sub_1405E26E0` requires `slot_array[slot].gen == key.gen` AND
`slot_array[slot].obj != 0`. A stale generation (slot recycled to a different
object) or an unpopulated slot both fail the check.

### Main Render Gate: `sub_1405D00A0`

Confirmed structure. After filling six render buckets, objects classified into
the deferred bucket (`manager + 792`, vtable `+0xC8` class, max 4 per frame) are
re-validated:

```c
object->vtable[0xD0](object, &key, scratch);   // writes current visibility key
if ((key & 0x7000000) != 0 || sub_1405E26E0(manager + 16, &key))
    sub_1405F79D0(manager + 8, object);        // submit to main render
else
    object->vtable[0]( object, 1 );            // SKIP / release
```

- Special-type keys (`key & 0x7000000`) bypass the slot check (always submitted).
- Ordinary type-0 keys must pass the 24-slot / generation / non-null check.
- The immediate-submit class (vtable `+0xC0` returns non-zero) is submitted
  without this re-check, but it still goes through `sub_1405F79D0`, i.e. it still
  competes for one of the 24 slots.

### Grid Rasterisation: `sub_1405CD980` -> `sub_1405C7B70`

`sub_1405CD980` reads each proxy's cached AABB via vtable `+0x30`
(`*(*obj + 48)`) and passes only the X/Z rectangle (Z extracted via
`_mm_shuffle_ps(..., 170)`) to `sub_1405C7B70`.

`sub_1405C7B70` confirmed details:

- Cells are **20 units** (`/ 20.0`); origin at `grid + 16 / +20` minus half
  extent (`grid + 24 / +28`).
- The rectangle is expanded by a fixed margin (`-20` low, `+40` span) before
  rasterisation, then clamped to `[0, grid+32 - 1]` (X) and `[0, grid+36 - 1]`
  (Z). The grid is finite.
- Marked cells are processed by `sub_1405C8460` / `sub_1405C81F0`, then a
  neighbour pass uses the 4-neighbour offset table `dword_14133ABE0` and a
  per-cell height (`cell + 0`) and flag bytes (`cell + 4`, `cell + 7`). This is a
  height/occlusion-style connectivity grid, 12 bytes per cell.

Note: the IDA string `aJ` / `"J..."` at `0x14133AC10` is data adjacent to
`dword_14133ABE0` that the disassembler mislabelled as text. It is the
neighbour-offset table, not a real string. (Avoid treating it as meaningful.)

### Proxy Relation Rebuild: `sub_1405CDA50`

Confirmed. Iterates `manager + 96 .. +104`; for proxies with byte `+100` set,
calls vtable `+0x10` to emit up to 8 relation entries (12 bytes each), pushed
into `manager + 232` via `sub_1405CF170`, then processed by `sub_1405CDBE0`, and
finally each proxy's vtable `+0x18` post-process is called. This is the
runtime-proxy relation/grouping graph that drives which objects are active for
the current frame.

### Why The Symptoms Match

1. **Center dependency.** The model's stage-object driver contributes a single
   cached AABB to the 20-unit X/Z grid. The per-frame proxy/grid visibility set
   (relation rebuild + grid + command `0x20000018`) decides which drivers are
   "active" (state `2`) and therefore get submitted and registered into the
   24-slot table. When the camera region no longer overlaps the grid cells that
   keep this driver active, the driver's object is not re-registered, its slot is
   not re-populated (or its generation goes stale), and `sub_1405E26E0` fails.

2. **Whole model vanishes at once.** The long ship is one runtime model instance
   behind one driver/key. The gate is per-object (per-key), not per-triangle, so
   the entire main model is skipped together.

3. **Shadow still renders.** The shadow / SDSM / depth-draw setup functions
   (`sub_14013ADC0`, `sub_140105010`, `sub_1401886B0`, `sub_1401877C0`) do not
   reference `object + 0x520`, `sub_1405E26E0`, or `sub_1405F79D0`. The shadow
   pass draws from a separate queue that is not gated by the 24-slot key table.

4. **File edits had no effect.** `.numatb` and `.numshb` file bounds never enter
   this path. The main-render gate is the runtime key/slot table populated in
   proxy-visibility order. Editing mesh AABB or materials cannot change slot
   registration order or the grid-cell activation.

### Confidence And Residual Unknowns

Confidence is high that the gate is the 24-slot keyed visibility system fed by the
proxy/grid visibility set. Residual items that would make this airtight (all are
optional and none change the conclusion):

- The concrete vtable `+0xC0` type value returned for the converted unit's driver
  (Stationary vs PhysicsProp), to confirm which of the two 24-slot pools it uses.
- The exact per-frame clear site that resets the `a1 + 600` bitmask / round-robin
  pool to empty before re-registration. The recycling behaviour is implied by the
  allocators (slots are reused once `obj == 0`), but the explicit clear was not
  pinned to a single address in this session.
- Whether the converted ship is registered as a single driver or whether the
  conversion should split it into multiple drivers so that off-center regions
  remain independently active.

### Practical Implication (Static Only, No Patching)

Per the non-goals, no memory patching was performed. The static evidence points
the fix toward the **asset/registration side rather than the renderer**:

- The problem is that one oversized model maps to one proxy/driver whose grid
  activation is center-biased. A converted stage/unit that spans many 20-unit
  grid cells is still represented by a single driver AABB and a single slot key.
- The most promising direction (to be designed and confirmed separately) is to
  make the converted model occupy the visibility system the way native large
  stage geometry does — e.g. multiple stage-object drivers / sub-parts so that
  each region keeps its own grid cells active and its own slot, instead of a
  single driver that deactivates when the camera leaves its center cell.



## Pure-IDA Follow-up And Corrections (2026-06-22, Session 3)

This section records a third IDA-only session. It pins down the slot lifecycle,
the visibility-rebuild internals, and corrects two earlier misreadings. All
offsets re-derived from `vsac27_Release.exe.i64` (image base `0x140000000`).

> Scope note: this session was instructed to stop touching asset files and work
> from IDA only. Asset-side facts referenced below were established in an earlier
> session and are repeated only where needed to interpret the runtime code.

### Correction 1: The 20-unit grid is a ground height-field, not a render grid

Earlier sections treated `sub_1405CD980 -> sub_1405C7B70` as the "render
visibility grid". This is wrong. The grid is a **terrain / ground height-field**
used by gameplay (walk height, landing, pathing), not a render cull structure.

Evidence:

- `sub_1405C7950` (grid init): `cellsX = ((sizeX + 200) / 20)` rounded to even;
  `sizeX (grid+24) = cellsX * 20`; every cell height initialised to
  `+inf` (`0x7F7FFFFF`).
- `sub_1405C8460` (per-cell mark): for each cell it builds a ray at the cell's
  world X/Z plus a height cap and calls `sub_14032E4B0(qword_14241E920, ray)`
  with ray length `2000.0`. `qword_14241E920` is the collision/physics world.
  On hit it writes the cell ground height and sets flag `cell+6 = 1`; on miss it
  writes height `2048.0` and clears the flags.
- The second pass in `sub_1405C7B70` (thresholds `0.1` and `6.0`, 4-neighbour
  table `dword_14133ABE0`) is a slope/step **connectivity** pass between cells.

So the driver's cached AABB only decides **which X/Z region gets ray-sampled for
ground height**. It does not gate main render. The grid's hard clamp to
`[0, cells-1]` is therefore irrelevant to the disappearance.

### Correction 2: `vtable+0xC0` is a runtime lookup, not a constant type

Both driver vtables resolve `+0xC0` to the same thunk `sub_1405EFA30`:

- Stationary vtable `0x14133E0F8`, slot `+0xC0` = `0x1405EFA30`.
- PhysicsProp vtable `0x14133E5D8`, slot `+0xC0` = `0x1405EFA30`.

`sub_1405EFA30` does **not** return a compile-time constant. It indexes a global
view/camera table (`qword_14241E880`, stride `*+56`, base `*+48`) using the
object's `+852/+856` fields and forwards to `(*(*(entry+32)+48))(entry+32)`.
The result `& 7` is the key type used by `sub_1405F7630`. So the type that
selects the slot pool (type-0 bitmask vs type-1/2 round-robin) is **view-state
dependent**, not fixed per class.

### Slot lifecycle: there is no "clear-all", only 3-frame deferred recycling

This resolves the earlier residual unknown about "the per-frame clear site".

- Sub-struct base for the render manager is `mainMgr + 22382`
  (`sub_1405D00A0(mgr+22382, mgr+22500)`).
- **No code clears the whole 24-slot pool each frame.** Recycling is per-object
  and deferred by 3 frames via `sub_1405CFFE0`:
  - `subStruct+784` is a mod-3 frame index; `subStruct+712 + 24*idx` are three
    pending-release lists.
  - Each frame, the list for the current index is drained: every object goes
    through `sub_1405F7A60`, then `(obj->vtable[0])(obj, 1)` destroys/recycles it.
- `sub_1405F7A60` mirrors the register split on `vtable+0xC0`:
  - `!= 0` -> `sub_1405F7400`: zero the 16-byte round-robin slot (`gen = 4095`).
  - `== 0` -> `sub_1405E2550`: `slot_array[slot] = 0`, `bitmask &= ~(1<<slot)`,
    remove from RB-tree, and overwrite the object key
    (`object+0x520` and `+0x528`) with the invalid value `slot | 0x80FFF000`
    (generation field = 4095).

Consequence: an object keeps its slot/key **as long as it keeps being submitted**.
Once it stops being submitted, the deferred list drains it within 3 frames; the
slot is freed and the key's generation is forced to 4095, so the next
`sub_1405E26E0` check fails. This is the concrete "slot becomes invalid" event.

### Driver registration count is asset-driven, not mesh-driven

Confirmed the chain that creates the runtime drivers:

- `sub_1405CC660` is the stage-load entry. `a2` is the loaded stage block;
  `a2[5]..a2[6]` is the stage-object descriptor array (32 bytes per entry).
  It first calls `sub_1405CA380(a1,0,0,0, a5=1, 1,1)` to make one root/special
  driver into `a1[9]`, then calls `sub_1405CCE10(a1, a2)`.
- `sub_1405CCE10`: `count = (a2[6]-a2[5]) >> 5`; for each descriptor it parses
  with `sub_1405CB050` and, for type `{1,2,3,5}`, calls
  `sub_1405CA380(..., a5=0, ...)` which pushes one grid/proxy driver into
  `manager + 96 .. +104` via `sub_1405CF0E0`.
- `sub_1405CB050` parses a **comma-separated text descriptor**
  (`sub_1401004C0` separator `44 = ','`, honours a `VDK_COMMENTOUT` marker).

So **driver count == number of stage-layout descriptor entries**, completely
independent of how many mesh objects the `.numshb` / `.numdlb` contain. One
descriptor referencing the whole converted model yields exactly one driver, one
runtime key, one activation unit.

`sub_1405CA380` driver class is chosen by `descriptor->m128_i32[0]`:
`0/1/2 -> Stationary` (`sub_1405F0010`, size `0x6A0`),
`3 -> PhysicsProp` (`sub_1405F0920`, size `0x6E0`), `>3` skipped.

### What `sub_1405C01E0` actually is: activation propagation, not camera cull

Full read of `sub_1405C01E0(visCtx)`:

Part A (only when `visCtx+648 != -1`): `visCtx+648` is a single **anchor key**
(the player/camera-focus object's runtime key). It walks a 64-byte-stride list
off the global scene root (`qword_1421158A0 + 370344..370352`) and, per matching
entry, calls `sub_1405E68E0`:

```c
// sub_1405E68E0(out, ptA, ptB, refAngle):
// angle = atan2(dx, dz) - refAngle, wrapped to (-pi, pi]
// |angle| <= 45deg   -> bucket 0 (front)
// |angle| >  135deg  -> bucket 1 (back)
// otherwise          -> bucket 2/3 (left/right by sign)
```

The accumulated bucket mask drives emission of command `0x20000018`
(`536870936`) with category `69/70/71/72` (the four directions) and
`payload+104 = anchor key`.

Part B (only when `visCtx+636 == 4`): enumerate all runtime keys from the RB-tree
(`*(visCtx+16) + 208`, up to 64 via `sub_140365C10`) in three passes:

1. For keys not yet at `state==2` (`!sub_1405E4FE0`) but valid
   (`sub_1405E5150`): read `slotData = *(visCtx+16) + 7456*slot + 16`; if
   `slotData+7448` (active byte) is set, read the two related-key references at
   `slotData+2704`, map them via `sub_1405E4DE0`, and increment a vote counter
   `visCtx + 55608 + 4*slot`.
2. If `+55608[slot] >= 2`, push to the `visCtx+248` list and bump
   `+55704[slot]`; otherwise reset `+55704[slot] = 0`.
3. Remaining non-`state==2` keys are pushed to the `visCtx+56 / +64` lists.

So Part B is **object activation/spawn propagation**: a key becomes active only
if at least two already-active related neighbours vote for it. There is **no
view-frustum or camera-matrix test anywhere in this system.**

### The state and key check functions (semantics nailed down)

- `sub_1405E4FE0(ctx, key)`: key -> slot -> `slot_array[slot].obj` ->
  `*(*(object + 11880)) == 2`. Note `object+11880` (`+0x2E68`) is a **pointer**;
  the dereferenced DWORD is the state. `state==2` is the object's gameplay
  lifecycle state (active/spawned), **not** "inside the camera frustum".
- `sub_1405E5150(ctx, key)`: key -> slot -> object -> `sub_1405E26E0` on
  `object+0x520`, i.e. "is this object's key still valid in the 24-slot table".
- `sub_1405E4DE0(ctx, out, key)`: validates `key` via `sub_1405E26E0`, then
  returns the related key stored at `object + 0x480` (`+1152`). This is the edge
  of the key graph (object -> its related object's key).
- `sub_1405E2770(table, key)`: same `state==2` check as `sub_1405E4FE0`.
- `sub_140602380(object)`: reads `object+0x520` and reports whether the object is
  currently registered (type-0 -> `sub_1405E26E0`; special bit `0x7000000` ->
  `sub_1405CFF30`). This is the per-object "am I registered right now" helper.

### Command-driven driver update path

- `sub_1405CE0D0(manager, cmdQueue)` consumes command `0x20000002`
  (`536870914`): per record, map `record+72` key -> slot to find the grid proxy
  in `manager+96`, and if proxy byte `+101` is set call
  `sub_1405EDD00(proxy, record+32, record+48, record+64)`, then set
  `record+20 = 4`.
- `sub_1405EDD00` pushes a 48-byte entry (two `OWORD` vectors + one int) into the
  proxy's `+224` vector. This is the proxy's relation/grouping data consumed by
  `sub_1405CDA50`, the same class of data as the vtable `+0x10` "up to 8 relation
  entries" path.

### Updated root-cause statement

The main-render gate is the 24-slot keyed visibility table
(`sub_1405E26E0` on `object+0x520`). The converted ship is **one stage-layout
descriptor -> one driver -> one runtime key -> one activation unit**, and it is
an **isolated node** in the related-key graph. Its activation depends on
propagation seeded from the single anchor key (player/camera focus), partitioned
into four directions by `sub_1405E68E0` and gated by a >=2-vote threshold. When
the focus moves off the ship's center region, propagation to the ship's key
breaks, the object stops being submitted, the 3-frame deferred recycler frees its
slot and invalidates its key (gen=4095), and `sub_1405E26E0` then fails -> the
whole main model is skipped. The shadow pass uses an independent queue and is
unaffected. This matches every observed symptom and is consistent with the
earlier asset-side finding that the ship is a single rigid unit bound to one
central bone.

### The keyed object is a ~12 KB gameplay entity, not the driver

`object+0x520` (the runtime key) is queried all over a method cluster around
`0x1405FC930 .. 0x140600000`, which is the stage-object-driver / entity method
family. But the object that owns `+11880` (the state pointer) cannot be the
driver: the drivers are only `0x6A0` / `0x6E0` bytes. The keyed object indexed by
`slot_array[slot].obj` is a much larger gameplay entity (~12 KB): it carries
`+0x520` (key), `+1104` (registered flag), `+11772` (a slot index into a separate
**21-entry** management table), and `+11880` (pointer to its lifecycle state
machine). `sub_1405FD390` is that 21-slot table's per-frame update; it resolves
each slot key via `sub_1405E4DA0(scene+179976, ...)` and reads
`+11772/+11784/+1104/+1120/+10648..10664`, confirming the entity layout.

### Remaining inference (not yet pinned statically)

The only link still resting on inference is **where `*(object+11880) == 2` is
written/cleared** (the entity spawn/despawn lifecycle state machine). Pinning that
write site would 100% close the "focus leaves center -> key drops out of the
propagation set" link.

None of this changes the conclusion or the asset-side direction (split the ship

## Follow-up: focus-relative gating (`sub_1405FF080`)

While tracing the 21-slot entity table (`sub_1405FD390`) we found the predicate
that decides whether an entity counts as "relevant" relative to the current
focus. This is the cleaner explanation of the center dependency than the
unresolved `state==2` writer.

`sub_1405FD390` resolves entity keys via `sub_1405E4DA0 -> sub_1405F7B00`
(key -> object lookup) and updates a separate **21-entry** management table
(`a1+8 .. a1+596`, 112 bytes per slot, loop cap `0x15 = 21`). It then calls
`sub_1405FFDE0`, which uses `sub_1405FF080` as its core gate.

`sub_1405FF080(mgr, a2, key, mode, a5)` returns whether the entity behind `key`
is active/relevant for the current focus:

- It reads two scene globals repeatedly: `v9 = *(scene+181056)` and
  `v10 = *(scene+181104)`. `v9` behaves as the **current focus key**
  (player / camera-target object).
- It resolves `key` to an entity (`sub_1405E47B0` + `sub_140602380` "is
  registered"), then reads entity fields `+11320` (a count), `+11686` (a flag),
  `+11768` (an id used to fetch an external record via the manager at
  `qword_14241E910+24`), and `+11800` (render-state, `+16`).
- The external record `v27` carries flags `v27[8]`, `v27[9]`, `v27[10]`,
  `v27[11]`; the final decision combines those flags, the `mode` argument
  (0/1/2), `sub_1405FEDB0(v9, key)` (relationship of the candidate to the focus
  `v9`), and direct comparisons `v9 == key` / `v9 == *(mgr+2432)` /
  `v9 == *(mgr+2440)`.

So entity relevance is decided by the entity's **relationship to the single
focus object `v9`**, not by any view-frustum test. An entity that the focus
"owns" or is related to passes; an unrelated entity only survives through the
spatial/direction propagation in `sub_1405C01E0`.

This is fully consistent with the root cause: the converted ship is a standalone
entity with one key and no gameplay relationship to the player focus, so it can
only stay active via spatial propagation seeded at the focus. When the focus
moves off the ship's center region, that propagation breaks, the entity stops
being submitted, the 3-frame recycler invalidates its key, and the main-render
gate `sub_1405E26E0` then fails. The asset-side direction is unchanged: give the
ship multiple stage-object descriptors / keys so each segment stays active on its
own rather than depending on one focus-relative propagation.
